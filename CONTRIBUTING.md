# Contributing to QuickZip

Thanks for your interest in QuickZip. Bug reports, fixes and improvements are
all welcome. This guide explains how to get set up and what makes a change easy
to accept.

## Before you start

- **Bugs and small fixes:** open an issue or a pull request directly.
- **New features or larger changes** (a new archive format, a new window or
  command, a change to how extraction works): open an issue first to discuss
  it. QuickZip follows a [high-level design](macos-archive-browser-hld.md), and
  agreeing on the approach first saves rework.

## Security

QuickZip opens archives from untrusted sources, so security bugs matter: path
traversal or symlink escapes during extraction, ZIP-bomb limits that can be
bypassed, crashes or out-of-bounds reads on malformed archives, quarantine not
being applied, passwords leaking.

Please **don't open a public issue** for these. Report them privately from the
repository's **Security** tab → **Report a vulnerability**, as described in
[SECURITY.md](SECURITY.md).

## Reporting a bug

Please include:

- your macOS version, your Mac (Apple silicon or Intel) and the QuickZip
  version or commit;
- what you did, what you expected, and what happened;
- the tool that made the archive, if you know it.

An archive that reproduces the problem helps most. **Don't attach an archive
containing private files.** If you can't share it, the output of
`quickzip verify --json` on it (see [docs/CLI.md](docs/CLI.md)) is often
enough: it holds no file contents, but it does include the archive's path and
the names of damaged items, so check those are fine to share first.

## Getting set up

You'll need macOS 14 or later and Xcode 16 or later.

1. Fork the repository and clone your fork.
2. Open `QuickZip.xcodeproj`. A fresh clone builds and runs as it is, signed to
   run locally. To sign with your own Apple Developer account, copy
   `Config/Local.xcconfig.example` to `Config/Local.xcconfig` (git ignores it)
   and set `BUNDLE_ID_PREFIX` and `DEVELOPMENT_TEAM`. Never commit your team ID
   or signing settings.
3. Run the tests: ⌘U in the `QuickZip` scheme, or from the command line:

   ```sh
   swift test --package-path ArchiveKit
   ```

ArchiveKit's tests also run on Linux with Swift 5.9 or later, which is handy
for engine work without a Mac.

The README's [Engineering](README.md#engineering) section covers fuzzing,
logging, strings and the iCloud Drive signing problem.

## Guidelines for changes

- **Keep ArchiveKit independent of the app.** The engine is a standalone Swift
  package with no UI code; the app talks to archives only through
  `ArchiveProvider`.
- **Extraction safety lives in one place.** Path sanitising, link checks,
  permission stripping and quarantine are in `ArchiveExtractor` and the
  `Extraction/` folder. A new format should feed that path rather than write
  files itself.
- **Treat every archive as hostile.** Read through the bounds-checked
  `BinaryReader`, respect `ArchiveLimits`, and fail with a specific
  `ArchiveError` rather than crashing.
- **Privacy in logs.** `os.Logger` messages hold counts, sizes and error kinds
  only, never item names, paths, contents or passwords.
- **User-facing text** goes in the String Catalogs (`Localizable.xcstrings`),
  with plurals and locale-aware formatting for numbers, sizes and dates.
- **Accessibility.** New controls need VoiceOver labels and keyboard access,
  and should work with Increase Contrast.
- **Tests.** Engine changes need unit tests. Fixture archives live in
  `ArchiveKit/Tests/ArchiveKitTests/Fixtures/` and are regenerated by
  `ArchiveKit/Scripts/make_fixtures.py`; add new fixtures there rather than
  committing archives made by hand where you can. Fixes for malformed-archive
  bugs should come with a fixture that reproduces them.
- **Performance.** If a change touches opening, searching or reading, run the
  benchmarks (`swift run -c release archivekit-bench` in `ArchiveKit`) and
  check the targets in the README still hold.
- Match the style of the surrounding code, and keep the README's status table
  and docs in step with what the change does.

## Pull requests

1. Create a branch in your fork from an up-to-date `main`.
2. Keep each pull request to one change, and explain what it changes and why.
   Link the issue it addresses, if there is one.
3. Say how you tested it. For UI changes, say what to look at (which window,
   menu or state), and add a screenshot if it helps.
4. Open the pull request against `main`. `main` is protected: changes reach it
   only through a pull request, and the maintainer merges.

Expect questions or requests for changes. QuickZip is maintained in spare time,
so a reply may take a few days.
